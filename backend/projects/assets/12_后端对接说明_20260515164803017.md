# 12_后端对接说明.md

## 一、文档定位

本文定义「对话实验室」日常对话 Agent 与前端、后端、记忆库、路由器、工作流平台之间的对接方式。

它主要给以下角色使用：

- 后端研发；
- 前端研发；
- Agent 工作流搭建人员；
- 数据库设计人员；
- 产品经理；
- 测试人员。

本文解决的问题是：

> 日常 Agent 不只是返回一句聊天回复。它每轮都要读取孩子小档案、家长长期关注、近期记录和待观察点，再返回自然回复、结构化判断、记忆候选更新、前端渲染字段和后端写库指令。

---

## 二、系统总体结构

推荐后端结构：

```text
前端 Chat UI
  ↓
API Gateway / Chat API
  ↓
Agent Router
  ↓
Context Builder / MemoryLoader
  ↓
Daily Agent
  ↓
Response Parser
  ↓
Memory Service
  ↓
Profile Service / Review Service / Rehearsal Service
  ↓
返回前端
```

一句话：

```text
前端只负责展示和交互；
Agent 负责判断和生成候选；
后端负责读取上下文、写入记忆、合并去重、返回真实更新结果。
```

## 三、核心模块分工

## 1. 前端 Chat UI

负责：

- 展示聊天气泡；
- 展示 memory_note 小字；
- 展示沟通预演卡；
- 展示成长信号卡；
- 展示按钮；
- 收集用户点击反馈；
- 发送用户输入和按钮事件。

不负责：

- 判断是否写入记忆；
- 伪造“已记录 / 已更新”；
- 自行生成孩子画像；
- 自行判断纠偏；
- 自行拼接 Agent 上下文。

---

## 2. Chat API

负责：

- 接收前端请求；
- 校验用户身份；
- 获取 family_id、child_id；
- 调用 Agent Router；
- 返回标准响应；
- 记录请求日志。

---

## 3. Agent Router

负责判断当前请求进入哪个 Agent 或模式。

可路由到：

```text
diagnosis_agent
daily_agent
communication_rehearsal_mode
stage_review_mode
questionnaire_summary_mode
```

日常对话默认进入：

```text
daily_agent
```

除非满足明显切换条件。

---

## 4. Context Builder / MemoryLoader

负责从数据库中读取和拼接 Agent 输入上下文。

读取内容包括：

- 当前用户输入；
- 最近对话；
- 孩子基础画像；
- 首次理解卡摘要；
- 相关孩子画像条目；
- 近期成长记录；
- 待观察点；
- 家长长期关注；
- 孩子问卷摘要；
- 家长画像；
- 家庭互动模式；
- 纠偏记录；
- 沟通预演记录。

---

## 5. Daily Agent

负责：

- 输出自然回复；
- 输出理解引擎摘要；
- 输出记忆更新候选；
- 输出沟通预演候选；
- 输出纠偏候选；
- 输出前端可展示按钮；
- 判断是否需要阶段复盘。

不负责：

- 直接写数据库；
- 直接决定最终 memory_note；
- 直接更新稳定画像；
- 绕过后端做长期记忆。

---

## 6. Response Parser

负责：

- 解析 Agent JSON；
- 校验字段完整性；
- 清理非法字段；
- 防止内部字段泄露给前端；
- 将候选更新转交 Memory Service；
- 将前台回复和后端写入结果合并。

---

## 7. Memory Service

负责：

- 根据候选更新判断是否写入；
- 合并重复记忆；
- 调整置信度；
- 写入成长记录、待观察点、长期目标；
- 处理纠偏；
- 写入更新日志；
- 返回真实 memory_note_final。

---

## 8. Profile Service

负责：

- 维护孩子主画像；
- 汇总 profile_entries；
- 合并画像条目；
- 更新 profile_summary；
- 处理画像降权、拆分、归档；
- 为下次对话提供画像快照。

---

## 9. Rehearsal Service

负责：

- 保存沟通预演记录；
- 读取历史预演；
- 关联后续沟通复盘；
- 支持“复制 / 存到预演记录 / 进一步解释”。

---

# 四、核心数据流

## 1. 普通日常对话流程

```text
1. 前端发送用户输入
2. Chat API 校验身份
3. Agent Router 判断进入 daily_agent
4. MemoryLoader 读取相关上下文
5. Daily Agent 生成回复和候选更新
6. Response Parser 校验输出
7. Memory Service 处理候选更新
8. 写入 profile_update_log
9. 返回 reply + actions + memory_note_final
10. 前端展示
```

---

## 2. 沟通预演流程

```text
1. 家长输入“我该怎么跟他说……”
2. Router 仍进入 daily_agent，但 message_type 为 communication_rehearsal
3. MemoryLoader 强化读取孩子画像、亲子互动模式、长期目标
4. Agent 返回沟通预演内容和 rehearsal_save_candidate
5. 前端展示按钮：复制｜存到预演记录｜进一步解释
6. 用户点击“存到预演记录”
7. Rehearsal Service 写入 rehearsal_records
8. 返回 memory_note_final：已存到预演记录
```

---

## 3. 纠偏流程

```text
1. 家长输入“不太像”或点击“不太像”
2. Router 标记 feedback_type = reject
3. MemoryLoader 读取被否定的旧判断和相关记录
4. Agent 返回 correction_candidates
5. Memory Service 降权 / 缩小范围 / 拆分 / 增加例外
6. 写入 correction_logs
7. 返回 memory_note_final：已调整前面的一个判断
```

---

## 4. 成长信号流程

```text
1. 家长输入孩子新变化
2. Agent 判断是否为 growth_signal
3. 返回 growth_record_candidates
4. Memory Service 判断是否写入 growth_records
5. 如果写入成功，返回 memory_note_final：已记录一个近期变化
6. 如果多条同向信号积累，Profile Service 可增强画像
```

# 五、推荐 API 设计

```json
  },

    "entry_mode": "daily_chat",
    "page": "chat",
    "last_message_id": "msg_123"
  }
}
```

### Response

```json
{
  "message_id": "msg_124",
  "conversation_id": "conv_001",
  "reply": {
    "message_type": "communication_rehearsal",
    "ui_badge": "已参考孩子小档案",
```

## 1. reply

前端只展示 `reply.content`，以及可选 `ui_badge`。

```json
{
  "message_type": "communication_rehearsal",
  "ui_badge": "已参考孩子小档案",
  "content": "这件事孩子可能先感受到的不是“英语要补”，而是“周末又少了一块能喘口气的时间”……"
}
```

---

## 2. understanding_engine

仅后端和调试可见，前端不展示。

用于记录：

- 输入拆解；
- 孩子候选解释；
- 家长关注；
- 家庭互动理解；
- 记忆写入原因。

前端不得展示该字段。

---

## 3. memory_note_suggestion

Agent 可以建议展示，但最终以后端写入结果为准。

```json
{
  "show": true,
  "text": "已记录一个近期变化",
  "detail": "孩子在作业场景中说出具体困难"
}
```

后端未写入成功时，前端不显示。

---

## 4. candidates

所有候选更新都只是建议，不直接等于写库。

后端需处理：

- 去重；
- 合并；
- 判断置信度；
- 写入；
- 降权；
- 返回真实结果。

# 八、message_type 规则

推荐枚举：

```text
normal_reply
growth_signal
communication_rehearsal
correction_reply
long_term_goal_update
questionnaire_summary
stage_review_suggestion
further_explanation
memory_update_reply
parent_pattern_note
```

## 前端展示建议

| message_type | 展示方式 |
|---|---|
| `normal_reply` | 普通聊天气泡 |
| `growth_signal` | 气泡 + 可选成长信号卡 |
| `communication_rehearsal` | 沟通预演卡 |
| `correction_reply` | 普通气泡 + 小字 |
| `long_term_goal_update` | 普通气泡 + 小字 |
| `stage_review_suggestion` | 可展示阶段小观察入口 |
| `further_explanation` | 展开解释气泡 |
| `memory_update_reply` | 普通气泡 + memory_note |
| `parent_pattern_note` | 普通气泡，不做诊断样式 |

---

# 九、ui_badge 规则

`ui_badge` 用于轻提示本轮参考了什么，但不要滥用。

可选：

```text
已参考孩子小档案
已结合近期记录
已参考孩子问卷
已结合长期关注
已参考沟通记录
已更新孩子小档案
```

展示规则：

- 只有真实读取过对应上下文才展示；
- 每轮最多展示 1 个；
- 不强行展示；
- 不要展示内部词。

禁止：

```text
已调用底层引擎
已完成画像推理
已识别家庭互动循环
已触发成长信号
```

---

# 十、memory_note 映射规则

前端展示的 `memory_note` 必须来自后端真实写入结果。

## 1. 允许展示

```text
已记录一个近期变化
已更新孩子小档案
已加入后续观察
已加入长期观察
已调整前面的一个判断
已存到预演记录
已补充孩子视角
已更新沟通理解
```

---

## 2. 映射关系

| 写入结果 | memory_note |
|---|---|
| `growth_records` 新增 | 已记录一个近期变化 |
| `profile_entries` 新增 / 增强 | 已更新孩子小档案 |
| `pending_observations` 新增 | 已加入后续观察 |
| `long_term_goals` 新增 / 增权 | 已加入长期观察 |
| `correction_logs` 新增 | 已调整前面的一个判断 |
| `rehearsal_records` 新增 | 已存到预演记录 |
| `family_interaction_patterns` 新增 / 增强 | 已更新沟通理解 |
| `profile_entries` 新增孩子视角条目 | 已补充孩子视角 |

---

## 3. 禁止前端伪造

不允许：

```text
Agent 说“这个值得记一下” → 前端直接显示“已记录”
```

必须：

```text
Memory Service 写入成功 → 返回 memory_note_final → 前端展示
```

# 十一、actions 规则

## 1. 普通画像反馈

```json
[
  { "label": "有点像", "action": "confirm" },
  { "label": "不太像", "action": "reject" },
  { "label": "补充一点", "action": "add_info" }
]
```

---

## 2. 沟通预演

固定：

```json
[
  { "label": "复制", "action": "copy" },
  { "label": "存到预演记录", "action": "save_rehearsal" },
  { "label": "进一步解释", "action": "further_explanation" }
]
```

---

## 3. 成长信号

```json
[
  { "label": "记一下", "action": "save_growth_record" },
  { "label": "不太像", "action": "reject" },
  { "label": "补充一点", "action": "add_info" }
]
```

---

## 4. 使用规则

- 按钮不要太多；
- 每条回复最多 3 个主按钮；
- 按钮文案要自然；
- 不用“确认正确 / 判断错误 / 重新生成”这类评测感文案。

# 十三、Memory Service 处理规则

## 1. 处理顺序

收到 Agent 输出后，建议按以下顺序处理：

```text
1. correction_candidates
2. profile_update_candidates
3. growth_record_candidates
4. pending_observation_candidates
5. long_term_goal_updates
6. parent_profile_candidates
7. family_interaction_candidates
8. rehearsal_save_candidate
9. profile_update_log
10. memory_note_final
```

纠偏优先处理，避免旧画像继续污染新写入。

---

## 2. 去重规则

写入前必须检查：

```text
同 child_id
同 category / scene_type
内容相似度高
近期已有同类记录
```

处理方式：

- 相似画像条目：合并；
- 相似长期目标：增权；
- 相似待观察点：更新时间和优先级；
- 相似成长记录：若为同一事件，不重复写；
- 相似家庭互动模式：增加 evidence_count；
- 纠偏记录：保留日志，但避免重复降权。

---

## 3. 置信度处理

建议规则：

```text
家长明确确认：+0.12
同类记录重复出现：+0.08
孩子问卷支持：+0.1
新事实冲突：-0.1
家长否定：-0.2
长期未出现：-0.05
```

置信度低于 0.6 的画像不进入稳定 summary。

---

## 4. 状态处理

`profile_entries.status` 推荐：

```text
hypothesis
active
confirmed
conflicted
deprecated
archived
```

`pending_observations.status` 推荐：

```text
active
resolved
archived
```

# 十四、Router 规则

## 1. 默认进入日常 Agent

满足以下条件：

- 已有 child_id；
- 有基础孩子画像；
- 家长是日常记录；
- 家长问当前事件；
- 家长要轻分析；
- 家长要沟通预演；
- 家长反馈“不太像”。

---

## 2. 切换诊断型 Agent 的条件

仅在以下情况考虑：

- 没有任何孩子画像；
- 家长首次进入；
- 家长明确要求整体深度分析；
- 当前多个问题无法由已有画像解释；
- 日常 Agent 返回 should_trigger_review；
- 近期纠偏很多，旧画像明显不稳。

---

## 3. 阶段复盘触发

如果 Daily Agent 返回：

```json
{
  "should_trigger_review": true,
  "review_reason": "近期多条记录显示旧画像需要阶段性重整"
}
```

前端可以展示入口：

```text
整理一次最近阶段的小观察
```

不要自动弹大报告。

---

# 十五、性能优化规则

## 1. 不全量注入历史

每轮只注入：

```text
最近 6–10 轮对话
高相关画像
近期成长记录
相关待观察点
相关长期目标
相关纠偏记录
```

不要把完整历史聊天塞给 Agent。

---

## 2. 场景检索

根据当前输入关键词检索相关记忆。

示例：

| 关键词 | 检索重点 |
|---|---|
| 作业、拖、磨蹭 | task_start / academic / family_interaction |
| 手机、游戏、短视频 | phone_rest / self_management |
| 沉默、不说话 | communication / parent_child_pattern |
| 成绩、考试 | exam_pressure / academic / resilience |
| 朋友、学校 | school_social |
| 责任感、自觉 | long_term_goals / self_management |
| 怎么说、要不要谈 | rehearsal_records / communication |

---

## 3. 上下文长度建议

```text
普通日常：3000–5000 中文字
复杂纠偏：6000–9000 中文字
阶段复盘：可单独走 summary 流程
```

---

## 4. 异步处理

可异步处理：

- 长期画像 summary 更新；
- 阶段复盘摘要；
- 低优先级日志；
- 统计分析。

应同步处理：

- 本轮回复；
- 按钮；
- 本轮 memory_note；
- 预演保存；
- 明确纠偏。

---

# 十六、错误处理

## 1. Agent 输出非 JSON

处理：

```text
1. 尝试 JSON 修复；
2. 若失败，仅返回 reply.content；
3. 不执行记忆写入；
4. 记录 raw_agent_output；
5. 前端不显示 memory_note。
```

---

## 2. Memory Service 写入失败

处理：

```text
1. 仍返回自然回复；
2. 不显示“已记录 / 已更新”；
3. 记录错误日志；
4. 可前端轻提示“本次记录稍后同步”。
```

推荐前台不要打扰用户，除非用户点击保存按钮失败。

---

## 3. child_id 缺失

处理：

```text
1. 不调用长期记忆；
2. 只进行普通回复；
3. 提示需要选择孩子档案；
4. 不写入孩子画像。
```

---

## 4. 重复点击保存

处理：

```text
1. 根据 message_id + action + candidate_id 幂等；
2. 已保存则返回已存在记录；
3. 不重复写入。
```

---

# 十七、权限与隐私

## 1. 记忆隔离

所有记忆必须以：

```text
family_id + child_id
```

隔离。

不要仅用 conversation_id。

---

## 2. 多孩子家庭

同一 family_id 下可有多个 child_id。

前端发送消息时必须带 child_id。

如果未选择孩子：

```text
不写入 child_profiles / profile_entries / growth_records。
```

---

## 3. 原始对话与结构化记忆分开

原始对话可用于回看和审计。

结构化记忆用于 Agent 后续调用。

不要把原始全文长期全量注入 Agent。

---

# 十九、上线最低标准

后端对接完成后，至少满足：

1. 每轮能按 family_id + child_id 读取孩子记忆；
2. Agent 能收到干净、相关、不过长的上下文；
3. Agent 输出 JSON 可稳定解析；
4. 前端只展示 reply、actions、memory_note，不展示内部字段；
5. memory_note 必须来自后端真实写入；
6. 成长信号能写入 growth_records；
7. 待观察点能写入 pending_observations；
8. 长期目标能写入 long_term_goals；
9. 纠偏能写入 correction_logs 并调整旧画像；
10. 沟通预演只有点击保存后写入 rehearsal_records；
11. 同类记忆能合并去重；
12. 家长评价不会污染孩子画像；
13. 新会话仍能调用同一孩子小档案；
14. 按钮点击具备幂等性；
15. 错误时不伪造“已记录 / 已更新”。

---

## 二十、最终一句话

日常 Agent 的后端不是简单的聊天接口，而是一套“孩子理解记忆系统”。

它每轮要完成：

```text
读对上下文
生成自然回复
返回结构化候选
后端审查写入
前端展示真实更新
下一轮继续调用
```

> 只有把 Agent、记忆库、前端小字和后端写入打通，用户才会真正感觉：这个系统不是一次性回答，而是在持续理解我家孩子。
